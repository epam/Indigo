# Bingo PostgreSQL 17 WAL Docker harness

This harness builds the patched Bingo PostgreSQL library directly from the current Indigo checkout, creates a PostgreSQL 17 runtime image containing that library, and runs the corruption/WAL regression suites against it.

No host CMake, compiler, PostgreSQL development headers, or manually copied `libbingo-postgres.so` are required. The only host requirements are Docker and the Compose v2 plugin.

## Image build

`Dockerfile` is a multi-stage build:

1. `bingo-builder` starts from `postgres:17-bookworm`, installs the native build toolchain and PostgreSQL 17 development headers, and runs Indigo's `package-bingo-postgres` CMake target against the current source tree.
2. `postgres-bingo` starts from a clean `postgres:17-bookworm` image and copies only the built `libbingo-postgres.so`, generated `bingo_install.sql`, source revision metadata, and test harness files into the runtime image.

The builder marks `/src` as a safe Git directory before CMake runs so Bingo's Git-derived version metadata is not lost to Git's dubious-ownership protection. This protects against the `1.9.1-00000000` fallback version observed in older container builds.

The generated runtime library is installed at:

```text
/usr/lib/postgresql/17/lib/libbingo-postgres.so
```

Fresh databases execute the `bingo_install.sql` generated by the packaged installer using PostgreSQL `$libdir` bindings.

Every test runner prints:

- the source `git describe` value;
- the exact source commit SHA;
- the SHA-256 of the built `libbingo-postgres.so`.

## Prerequisites

- Docker
- Docker Compose v2 (`docker compose`)
- this repository checked out at the branch/commit you want to test

All credentials and databases created by this harness are disposable test data only.

## Quick start

From the repository root:

```bash
bash bingo/postgres/tests/docker/run.sh build
bash bingo/postgres/tests/docker/run.sh normal
bash bingo/postgres/tests/docker/run.sh concurrent
bash bingo/postgres/tests/docker/run.sh crash
bash bingo/postgres/tests/docker/run.sh replica
```

Run everything:

```bash
bash bingo/postgres/tests/docker/run.sh all
```

Remove containers and all persistent harness volumes:

```bash
bash bingo/postgres/tests/docker/run.sh down
```

A source change invalidates the Docker build context automatically. Re-running any test command rebuilds the image as needed before starting the suite.

## Suites

### `normal`

Runs `postgres_wal_build_test.sh` against a normal PostgreSQL 17 primary and covers:

- initial Bingo `CREATE INDEX`;
- transaction rollback;
- incremental insert;
- a non-key indexed-column update that still invokes Bingo for a new heap TID;
- DELETE + VACUUM/Bingo bulk deletion;
- `REINDEX`;
- result consistency across rebuild;
- physical tail-page inspection for zero/uninitialized pages;
- basic WAL-volume reporting.

```bash
bash bingo/postgres/tests/docker/run.sh normal
```

The primary is exposed on host port `55432` by default. Override it with `BINGO_TEST_PRIMARY_PORT`.

### `concurrent`

Runs the concurrent-writer regression that reproduces the class of failure reported by upstream issue #108 and mixes in non-key updates.

```bash
WORKERS=12 ROWS=12000 \
  bash bingo/postgres/tests/docker/run.sh concurrent
```

Writes to one Bingo index are expected to serialize in the patched access method; this test verifies correctness rather than parallel write throughput.

### `crash`

Runs `postgres_wal_recovery_test.sh` against a dedicated disposable PostgreSQL instance. Its `PGDATA` is tmpfs-backed and the test deliberately executes:

```text
pg_ctl stop -m immediate
```

while Bingo is mutating its index. The container remains alive and restarts PostgreSQL so crash recovery can be checked.

This service does not crash the normal Compose primary and does not mount the Docker socket.

```bash
bash bingo/postgres/tests/docker/run.sh crash
```

Stress parameters can be adjusted without modifying Compose:

```bash
CRASH_ROWS_BASELINE=100000 \
CRASH_ROWS=300000 \
CRASH_DELAY=0.10 \
  bash bingo/postgres/tests/docker/run.sh crash
```

The suite checks that aborted heap rows do not become visible through Bingo, searches and new writes still work after recovery, VACUUM can complete after recovery, and the Bingo relation does not end with the zero-page signature seen in the original failure.

### `replica`

Starts a fresh primary and physical PostgreSQL standby using `pg_basebackup -R`. Both servers use the same source-built `postgres-bingo` image.

```bash
bash bingo/postgres/tests/docker/run.sh replica
```

The replica suite verifies physical WAL replay for:

- initial Bingo bulk build;
- incremental inserts;
- non-key updates that invoke Bingo;
- DELETE/VACUUM changes;
- `REINDEX` relation replacement.

It waits for the standby to replay through a target WAL LSN and compares Bingo query results between primary and standby. The wrapper removes harness volumes before this suite so the standby is always based on a fresh backup of the primary under test.

## Direct Compose use

The wrapper is only convenience. From this directory:

```bash
cd bingo/postgres/tests/docker

docker compose build primary
docker compose up -d primary
docker compose --profile tools run --rm runner normal
docker compose --profile tools run --rm runner concurrent

docker compose --profile crash run --rm crash-test

docker compose --profile replica up -d primary standby
docker compose --profile replica run --rm replica-test replica
```

## Inspecting the normal primary

```bash
bash bingo/postgres/tests/docker/run.sh shell
```

or from the host:

```bash
psql 'host=127.0.0.1 port=55432 dbname=test user=postgres password=postgres'
```

Follow PostgreSQL logs with:

```bash
bash bingo/postgres/tests/docker/run.sh logs
```

## Build/test provenance

The source checkout is the single source of truth. The harness does not download a released Bingo binary and does not consume a manually supplied `.so`.

The builder runs Indigo's normal PostgreSQL packaging target, generates the installation SQL from that package, and hands those artifacts to the clean runtime stage. The runtime image stores:

```text
/opt/bingo-harness/source-describe
/opt/bingo-harness/source-revision
/opt/bingo-harness/libbingo-postgres.sha256
```

These are printed before the normal, concurrent, and replica suites so test output can be tied directly to the built source and binary.
